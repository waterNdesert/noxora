# Rebuild Risk Analysis, Pitfalls & Commercial Complexities

This document details technical, operational, integration, and commercial risks associated with rebuilding and operating an enterprise platform with Onyx's scope, along with concrete mitigation strategies.

---

## 1. Technical & Architectural Risks

### A. OpenSearch Memory Exhaustion & Vector Sizing
- **Risk Profile**: High | **Impact**: Critical (Service Outage)
- **Problem**: Storing millions of 1024-dimensional dense vectors alongside standard BM25 text indices can exhaust JVM heap memory or Linux virtual memory maps, triggering circuit breaker exceptions (`429 Too Many Requests`).
- **Mitigation Strategy**:
  - Configure OpenSearch JVM heap to strictly 50% of container memory (up to 31 GB max to preserve compressed object pointers).
  - Employ scalar vector quantization (SQ) or Product Quantization (PQ) in OpenSearch `hnsw` index definitions to cut vector memory footprint by 75%.
  - Partition document sets across separate dedicated index shards.

### B. Embedding Model Lock-In & Re-indexing Downtime
- **Risk Profile**: High | **Impact**: High (Operational Disruption)
- **Problem**: Vectors generated by one embedding model (e.g., `BAAI/bge-large-en-v1.5`) cannot be compared against vectors generated by another (e.g., `text-embedding-3-large`). Switching models requires re-embedding every chunk across the entire corpus.
- **Mitigation Strategy**:
  - Adopt Onyx's dual-index swap pattern (`swap_index.py`). Write new chunks to an auxiliary staging index while the primary index continues serving queries. Once catch-up indexing finishes, execute an atomic alias switch.

### C. Streaming Duplex Proxy Memory Growth
- **Risk Profile**: Medium | **Impact**: Moderate (Node.js High Memory)
- **Problem**: Routing real-time SSE token streams through the Next.js API proxy (`web/src/app/api/[...path]/route.ts`) forces Node.js to maintain open duplex streams for every active user. Under thousands of concurrent chat turns, Node.js memory rises sharply.
- **Mitigation Strategy**:
  - In production, configure Nginx, Traefik, or an AWS Application Load Balancer to route `/api/*` directly to the Uvicorn/FastAPI port, bypassing Node.js entirely for streaming traffic.

## 2. External Integration & Third-Party API Risks

### A. OAuth2 Refresh Token Expiration & Desynchronization
- **Risk Profile**: High | **Impact**: Data Sync Interruption
- **Problem**: Upstream providers (e.g., Google Workspace, Microsoft Graph, Salesforce) frequently expire refresh tokens due to enterprise admin policy resets, inactivity, or password changes.
- **Mitigation Strategy**:
  - Implement a proactive token health check (`oauth_refresher.py`) that tests token validity before starting an ingestion crawl.
  - Automatically flag the `ConnectorCredentialPair` as `AUTH_EXPIRED` and email the workspace admin with a 1-click re-authorization link.

### B. Upstream API Rate Limiting (HTTP 429)
- **Risk Profile**: High | **Impact**: Ingestion Delays
- **Problem**: Crawling hundreds of thousands of files across Google Drive or Jira easily hits tenant API rate limits, stalling background workers.
- **Mitigation Strategy**:
  - Implement exponential jittered backoff in all connector request adapters.
  - Partition large crawl jobs into granular batches stored in Redis queues, allowing Celery workers to interleave calls across different data sources.

## 3. Commercial, Proprietary & Legal Complexities

### A. Third-Party App Store Verification Requirements
- **Challenge**: Operating public Slack, Google Workspace, or Microsoft Teams integrations requires submitting applications for formal vendor security reviews (e.g., Google OAuth App Verification, Slack App Directory Review).
- **Reality**: These reviews can take 4–8 weeks and require public privacy policies, SOC 2 compliance documentation, and domain verification.
- **Recommendation for Rebuilders**: For internal company deployments, configure "Custom Internal Apps" within your enterprise Google / Slack consoles to bypass public marketplace reviews.

### B. Proprietary Commercial Features vs. Open Source
- **Observation**: Features such as SAML 2.0 SSO, automated permission synchronization, multi-tenant schema isolation, whitelabeling, and usage quotas reside in Onyx's proprietary `backend/ee/` directory.
- **Recommendation**:
  - Recreating these features from clean-room architectural designs is fully viable using standard open-source libraries:
    - SAML 2.0: `python3-saml` or `pysaml2`.
    - Multi-Tenancy: PostgreSQL schema-level isolation using SQLAlchemy dynamic `search_path`.
    - Whitelabeling: Dynamic CSS variables loaded via API and injected into the Next.js root layout.
